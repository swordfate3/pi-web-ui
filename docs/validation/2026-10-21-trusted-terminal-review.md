### Important (Should Fix)

#### I1 — P2: Interactive control is enabled before any complete screen has rendered

- **Primary locations:** `src/web/terminal/app.ts:61`, `:66`, `:240`, `:339`, `:357`. Related integration: `hub/terminal-server.ts:325` deliberately sends `ready` before initial screen delivery; `src/web/terminal/app.ts:177` clears the current view before asynchronous replacement rendering.
- **Defect:** `ready` sets `connected = true`, cancels the connection timer, creates an assembly, and enables Acquire. An acquire ACK then enables text, fixed keys, and resize solely from connection/lease/pending/composition state. Neither `controls()` nor the actual `send()` guard requires a completed, identity-validated, rendered screen. The asynchronous `restore()` path has a timeout but no input-readiness fence while that timeout is outstanding. Thus transport readiness plus a valid lease is treated as sufficient for interactive readiness.
- **Concrete evidence:** I ran the named, bounded, nonmutating **`whole-branch-screen-readiness`** probe against the production browser entry bundled in memory with its real wire validators. Only DOM/socket boundaries and xterm's completion callback were controlled, reusing the boundary fixture definitions without executing its registered tests. Three fresh cases were exercised: (a) `ready` with no screen frames; (b) `screen-start` without the rest of the first snapshot; (c) a valid first snapshot with the render callback withheld. In all three, Acquire and Send were enabled, zero renders had completed, and explicit clicks emitted `attach → acquire → input`. Cases (a)/(b) had zero terminal views; (c) had one uncompleted view. This was not a suite rerun, network/PTY write, or claim that a forged server can bypass the sink.
- **Why it matters / severity:** The approved design §6 requires incomplete/unreliable reconstruction to reject interactive attach. A legitimately authorized user can currently send Enter, confirmation text or another command before seeing a complete native prompt, including the normal first-render window on a slow client. A later render failure/disconnect cannot undo bytes already written. This is a concrete safety/plan-compliance gap deserving an Important/P2 correction before merge, not a Critical privilege-escalation claim.
- **Direction:** Track screen readiness separately from transport and lease readiness, scoped to the current generation/identity. Keep acquisition and all actual input/resize dispatch disabled until a complete valid initial snapshot has successfully rendered. Clear that readiness on disconnect/identity change/invalid screen and whenever the displayed view is cleared for replacement; alternatively preserve an explicitly valid view until a replacement is ready. Apply the fence in dispatch as well as button state. Bound initial screen establishment. Add focused cases for no first screen, partial first assembly, held/failed first render, successful completion, replacement render, and late completion after disconnect. Preserve the existing serialized render queue, draft-revision ACK behavior, and no-retry policy; do not resolve this by weakening validation or letting a timeout certify readiness.
- **Existing test blind spot:** `tests/hub-terminal-browser.test.ts:188`'s acquire helper intentionally obtains control after only the fixture's `ready`, and its input/ACK tests do not first complete a screen. The current server success test waits for `screen-end` (`tests/hub-terminal-server.test.ts:147`) but does not establish the browser render fence. Passing these tests therefore does not contradict the reproduction.
